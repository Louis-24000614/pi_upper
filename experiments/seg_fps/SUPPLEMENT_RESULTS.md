# 道路分割补充优化实测

按 07 补充建议继续验证，最终候选保持 Lite、三个 context `1,2,4`、OpenCV 原配置 8 线程，只把 NumPy/BLAS 限为 1 线程。原 200ms 保护不变，稳定性按用户最新要求执行 300 秒；完成后保持设备开机。

## 正式结果

五组交替 A→B／B→A，每版每轮 60 秒。固定同一合法最高频率：CPU 小核 1.8GHz、大核 2.4GHz，DDR 2.4GHz，NPU 1GHz。频率收益不算入代码收益。双方每 context 相同 20 次预热，逐次耗时保存在原始 JSON；初始化和预热不计入窗口。

| 指标 | BLAS 8 线程 | BLAS 1 线程 |
|---|---:|---:|
| 完整视觉回放 FPS | 22.55 | 34.69 |
| 单帧工作 P95（ms，逐轮平均） | 151.56 | 89.93 |
| 消费后帧龄 P95（ms，逐轮平均） | 194.11 | 105.78 |
| 进程 CPU（可超过 100%） | 673.3% | 221.6% |
| 平均峰值 RSS（MiB） | 541.6 | 548.0 |
| 工作超过 200ms／完成结果 | 11/6766 | 0/10408 |

逐对增益平均 **53.84%**，标准差 1.94 个百分点，范围 52.13%～57.35%。正式吞吐模式包含合法停车意图，未做帧龄门控，不将它当作实际可用控制率。

后处理均值 12.81→3.49ms；推理调用均值 87.61→68.27ms。减少 BLAS 线程既降低小矩阵启动/调度开销，也减轻其他阶段的 CPU 争抢；调用墙钟下降不能全部归于 NPU 算子加速。

保留 BLAS=1；CV=1 和 BLAS=2 在最终 CV=8 条件下变慢，未采用。C 标准/输入绑定收益没有超过短测波动，继续用 Lite。输入绑定会把工作移入 rknn_run，不能单凭 input_io_ms 下降宣称总开销下降。频率与代码收益单独报告；应用入口不自动固频，需要使用 run_with_frequency 启动器显式选择，退出后恢复原配置。

输出 IO 分项有实测，应用层 `.copy()` 平均约 1.3ms，原生输出查询显示 FP16 与打包布局：prototype 原生打包存储 4,915,200 字节，标准逻辑属性的 FP16 尺寸 1,638,400 字节，当前 want_float 获取的该输出为 3,276,800 字节。仅此属性不能证明整个模型为 FP16。当前主要收益来自 CPU 线程预算，暂不删除所有权复制、不绑定原生输出；后续若推进，必须验证打包布局和 FP16 转 float 的全部成本。

六 context 是筛选项，不自动扩大此前接受三个 context 的延迟权衡。完整链路/实时帧龄和资源代价见上表及原始 JSON；生产入口保持最多三个 context。混合负载是障碍 5Hz、刀具参考图 1Hz、人脸检测 2Hz，人脸输入未包含人脸，未验证特征提取负载；CPU 统计不含外部识别服务进程。

## 实际流水线与正确性

在合法最高频率下，实际 OrderedSegmentStream 连续 **300 秒**：处理 10066 帧／33.55 FPS，通过导航前 200ms 门的 10066 帧／**33.55 FPS**，过期 0，工作超过预算 0，旧来源与乱序均为零，异常为零。帧龄门在导航前检查，不能据此保证导航结束时仍小于 200ms。

工作 P95 95.91ms、导航后帧龄 P95 106.13ms，属于最后 4096 个诊断样本；总处理率覆盖完整窗口。温度 35.2～46.2℃，峰值 RSS 527.2MiB；最后 120 秒 RSS 范围 403.0～502.1MiB。这是五分钟验证，不外推为三十分钟稳定性。

## 使用与复现

在独立分支 codex/seg-fps-ab；原 pi_upper/main 的用户文件未改。新增开关默认不改变原配置，板端已有 threadpoolctl；其他环境只在请求 BLAS 调优时需要该可选依赖。

```bash
cd /home/orangepi/pi_upper_seg_fps
export PYTHONPATH=.:navigation:vision
/home/orangepi/vision_compare_pi_upper/bin/python -m road_follow \
  --fps-opt --correct-nms --npu-contexts 3 --blas-threads 1
```

上述为正常调频的应用开关示例。最终固频组合应使用 python -m experiments.seg_fps.run_with_frequency --policy all-max -- python -m road_follow --fps-opt --correct-nms --npu-contexts 3 --blas-threads 1 --heap-trim-interval 60；启动器先授权 sudo，仅调频子命令以 root 执行，主程序仍以原用户运行，正常退出及 INT/TERM/HUP 会等待主程序退出后恢复频率。性能素材冻结于 /home/orangepi/seg_fps_data，模型和相机标定的 SHA256 见 SUPPLEMENT_SUMMARY.json；没有覆盖最新生产相机标定。应用开关不会自行打开串口，实车参数按项目配置另行验证。

新增 run_with_frequency.py 提供独立进程组停止、sudo 票据续期及退出恢复，frequency.py 保存 sysfs 原配置，提供 original/ddr-max/all-max 对照与明确读回检查；每个实验脚本均在退出/中断时恢复，最后 min/max/governor 已逐域比对一致。GPU、OPP、电压和温控未改。

分项计时中 input_io/run/output_io/Python 输出复制均嵌套于 rknn_ms，mask 子项嵌套于 post_ms，禁止重复相加。mask 子项仅在有效框时存在，JSON 保留 count，不能将条件样本均值直接相加成全部帧均值。pure、seg、full 的 FPS 使用各自模式的完成口径，不用不同模式 FPS 相减估计阶段耗时。

模型原生 IO 定义和布局处理依据：[RKNN API](https://github.com/airockchip/rknn-toolkit2/blob/master/rknpu2/runtime/Linux/librknn_api/include/rknn_api.h)、[官方 YOLO11 IO 示例](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolo11/cpp/rknpu2/yolo11_zero_copy.cc)。实际属性以本次板端 native_output_attributes.jsonl 为准。

## 内存回收对照

正常调频的五分钟实际程序为 19.78 处理 FPS / 18.18 有效更新 FPS。合法固频加 BLAS 单线程达到 33.64 FPS，但默认堆策略五分钟 RSS 后段仍升高。限制 arena 数量并未使 RSS 收敛；固定 mmap/trim 阈值短测降到 28.45 FPS，均不作为最终设置。

单独 malloc_trim 仍未充分回落，最终每 60 秒先 gc.collect 再 malloc_trim(0)。回收器记录不可达对象数、GC/trim 分项时间和回收前后 RSS；不释放仍在使用的 tensor，不改变数据精度。最终保持原分配策略，不设置 MALLOC_*。回收开关默认关闭，只作用于本程序。

| 周期 | GC（ms） | trim（ms） | 不可达对象 | 回收前→后 RSS（MiB，即时观测） |
|---|---:|---:|---:|---:|
| 1 | 29.07 | 16.86 | 250 | 483.9→273.0 |
| 2 | 40.01 | 16.54 | 632 | 488.0→274.9 |
| 3 | 30.76 | 19.11 | 322 | 513.8→278.2 |
| 4 | 32.16 | 18.84 | 516 | 491.8→288.4 |
| 5 | 32.57 | 20.19 | 450 | 500.8→264.6 |

即时读数与每十秒的正常采样口径不同；线程恢复后会重新申请临时数组，不能把瞬时低值当成全部运行时 RSS。末次回收接近退出清理，不据此证明更长运行无泄漏。五分钟内周期采样可重复回落，峰值和全部曲线保存在原始 JSON。

一秒间隔 GC/trim 下三 context 并发 20 帧专项通过：tensor、mask、顺序、持有结果与软件速度序列一致。启动器子命令退出码 7、SIGINT、SIGTERM 三项实际恢复检查通过。88 项道路测试包含回收后仍持有数组的内容保护及异常退出停止后台线程。

依据：[GNU libc 分配器参数](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)、[Linux malloc_trim 接口](https://man7.org/linux/man-pages/man3/malloc_trim.3.html)。回收来源是否主要为 ctypes 引用环仍是推断，本次没有逐一归因。
