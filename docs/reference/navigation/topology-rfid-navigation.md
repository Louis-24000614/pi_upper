# 拓扑定位、RFID 到点与路口转向

本文统一说明巡逻任务中三个容易混淆的问题：小车怎样知道自己在场地哪里，现场标签编号怎样与固定位置分离，以及有标签、无标签路口分别用什么信号停车转向。

## 核心约定

场地道路结构和巡逻位置是固定的，标签中的编号在比赛现场不假定与图示位置号相同。因此必须分开保存：

| 名称 | 含义 | 示例 |
| --- | --- | --- |
| `slot_id` | 固定物理巡逻位置，即拓扑节点 | `2_1`（左侧第 2 行） |
| `card_number` | 底部读卡器实际读出的 1～12 | `7` |
| `current_node` | 最近一次确认到达的拓扑节点 | `2_2` |
| `next_node` | 当前路径期望到达的节点 | `2_1` |
| `current_edge` | 正在行驶的固定道路段 | `2_1__2_2` |
| `s` | 从上一节点起沿当前边走过的距离 | `0.63 m` |

例如车到达固定位置 `2_1` 后读到 7 号卡，应记录：

```text
slot_to_card["2_1"] = 7
card_to_slot[7] = "2_1"
visited_cards[7] = true
```

不能因为读到 7 就把车辆物理位置改成图示的“⑦”。图示编号只方便读图，不作为运行时定位依据。

## 小车怎样知道所在位置

本方案采用先验拓扑定位，不做依赖厘米级全局坐标的 SLAM：

1. 比赛开始时，起点 `0_0` 和车头朝向已知。
2. 全局规划器在 `config/nav_topology.yaml` 上生成节点序列。
3. 执行器记住刚离开的 `current_node`、当前 `current_edge` 和 `next_node`。
4. 视觉负责沿路居中并发现路口；编码器只累计当前边的进度 `s`。
5. 到点信号与预期节点、预计边长、可见路口类型一致后，才推进节点状态并把 `s` 清零。

出发区顶端不是两条从 `0_0` 发出的斜边，而是一个真实丁字路口：

```text
         0_0
          │  0.15 m
1_2 ──── 0_J ──── 1_3
 │                  │
2_2                2_3
```

因此起步有限动作只执行 `0_0 → 0_J`。收到这 15 cm 的 `FORWARD_DONE`
后，必须先向 Agent 上报到达 `0_J`，再根据下一条边决定原地左转或右转。
当前配置的首次出口是 `1_2`，所以默认动作是右转；它不是写死在起步状态机中的方向。

典型状态如下：

```text
current_node=2_2
next_node=2_1
current_edge=2_1__2_2
heading=WEST
s=0.63m
```

拓扑定位依赖“已知起点 + 已执行的选岔”。单独一幅对称十字路口画面无法判断它是全场哪一个路口，因此出现与路径不一致的路口或距离时，不得盲目推进 `current_node`。

## 两类到点与转向方式

节点配置需要明确区分 `patrol_slot` 和普通 `junction`。两类节点共用拓扑规划，但停车触发信号不同。

到达判据由当前规划的 `next_node.role` 选择，不要求同一种传感器覆盖所有节点：

| 目标节点类型 | 最终到达证据 | 辅助门限 |
| --- | --- | --- |
| `patrol_slot` | 扫描到一次新的有效 RFID 标签 | 未提前读到卡时，侧边角和正前方检测带只用于最后 20 cm 接近 |
| `junction` | 侧边角已锁存，正前方检测带稳定无路，并完成唯一一次 20 cm | ODOM 已进入当前边末端窗口 |

`card_number` 只回答“这个物理位置放了几号卡”，不回答“车辆在拓扑中的哪个节点”。具体节点始终由已知起点、已执行路线和当前预期的 `next_node` 决定。

### 有 RFID 标签的巡逻位置

当前策略是：底部读卡器产生新的有效读卡事件后，认为到达当前路径所期望的 `patrol_slot`，先停车并上报到点，再按照拓扑路径执行直行、左转、右转或沿来路倒回。

```text
视觉循迹接近 patrol_slot
    ↓
RFID_CARD: present=1, card_number=1..12, generation 变化
    ↓
停止 CMD_VEL，并确认车轮已经停稳
    ↓
确认 expected next_node 是 patrol_slot
    ↓
记录 slot_id ↔ card_number，按卡号去重并播报
    ↓
产生 NODE_REACHED(expected next_node)
    ↓
根据入边和出边选择 STRAIGHT / LEFT / RIGHT / BACKTRACK
    ↓
视觉重新捕获新道路，进入下一条边
```

接近标签时不再因一次 `stop_lookahead` 反复分段搜索，也不再允许累计盲走 350 mm。当前策略是：

1. 左右任一侧矮沿端头连续出现 2 帧后，只锁存“正在接近巡逻点”；
2. 仍使用 Pure Pursuit 视觉循迹，侧边角消失本身不触发动作；
3. BEV 正前方 `0.34..0.48 m` 检测带的 road mask 占比连续 3 帧不高于 10%，且近处道路仍安全时，下位机以 50 mm/s 锁航向前进唯一一次 200 mm；
4. 这 200 mm 内持续接收 RFID；读到标签立即发送 STOP，停车 2 秒后按拓扑执行动作；
5. `FORWARD_DONE` 后仍未读到卡则锁定停车，禁止再发第二段。

未先看到侧边角、整幅道路分割不安全，或推理超时时，都不启用这 20 cm。

后续动作来自规划路径中的“入边 → 出边”，不能由 `card_number` 决定，也不能让道路分割在对称路口自行猜测。执行器应按拓扑关系选择直行、左转、右转或沿来路倒回，不能默认左转。

巡检接近日志需要分别保存 `edge_left_seen` 和 `edge_right_seen`。因此即使固定前进后侧路已经退出画面，仍能打印本次接近过程中曾看到“左侧”“右侧”或“两侧”。同时打印当前规划的固定 `slot_id` 和现场读到的随机 `card_number`，例如 `位置=2_1，标签=7，侧边=左侧`；这只是观测记录，侧边方向和标签号码都不替代拓扑的入边/出边转向计算。

`RFID_CARD` 以 10 Hz 周期上报，任务层只把 `generation` 的新变化当成一次候选到达事件。同一张卡持续在读卡器下方时不得重复触发本次到达；车辆离开、收到 `RFID_REMOVED`，以后沿路线重新回到该节点时，同一卡号的新事件仍可确认新一次到达，但 `visited_cards` 保证它不重复计分和播报。

首次到达某个物理位置时，以当前预期节点建立随机摆放映射。例如当前路线为 `2_2 → 2_1`，末端读到 7 号卡，应确认到达 `2_1` 并记录 `2_1 ↔ 7`，不能把当前位置解释成图示的第 7 个位置。再次到达时映射必须一致；卡号已经绑定到其他 `slot_id` 或当前位置读到不同卡号时停车报警。

相邻两个节点都有标签时（当前拓扑中的 `5_2 ↔ 5_3`），必须先确认起点卡已经移出读卡区，再接受新的 `generation`。这样不会把 `5_2` 的残留读数误判为已经到达 `5_3`。

### 没有 RFID 标签的普通路口

普通 `junction` 继续采用视觉路口方案：

1. ODOM 进入当前边的末端窗口后，才允许接受本边的路口候选，防止过早推进拓扑。
2. 道路分割连续多帧发现侧边角并锁存；侧边角只证明“这里有路口”，不直接触发前进。
3. 继续视觉循迹，直到正前方检测带 `fband <= 0.10` 连续 3 帧，并用 `corridor_end_y_m`、车道宽度和横向偏差作安全门限。
4. 下位机用编码器固定前进最后 200 mm；航向目标取上电基准和已完成转弯维护出的当前小车方向档位，实时 IMU 只反馈误差，不使用动作开始瞬间的 yaw 重新置零。
5. 收到 `FORWARD_DONE` 后，才产生 `NODE_REACHED(expected next_node)` 并清零本边进度。
6. 根据下一条边执行直行或转向，随后由视觉重新捕获中心线。

具体交接条件和日志字段见 [视觉路口与里程计补盲转弯](vision-odom-junction-turn.md)。RFID 不参与普通路口判断，因为这些节点本来就没有标签。

前三条隧道 `2_2__2_3`、`3_2__3_3`、`4_2__4_3` 的两端都是 `junction`，因此仍采用“ODOM 末端门限 + 隧道出口后的稳定路口视觉 + 定距到中心完成”确认；明暗变化只能作为辅助。第四条隧道 `5_2__5_3` 的两端都是 `patrol_slot`，采用新的 RFID 事件确认。

## RFID 停车点的机械标定

“读到标签即停车”不一定等于“两轮旋转中心已经到达路口中心”。需要实测三个位置：

- 标签在路口中的安装中心；
- 读卡器天线有效感应区中心；
- 两个驱动轮轴线中点，即原地旋转中心。

若天线中心与旋转中心沿车身方向存在偏移，应在首次读卡后低速补偿该固定距离，再停车转向；若两者基本重合，补偿距离可为 0。停车惯性也计入这项标定。补偿必须是小范围安装参数，不能用一整格固定里程代替视觉循迹。

## 路径状态推进顺序

一次转向不能只更新朝向，必须同步推进拓扑状态：

```text
到达 next_node
→ current_node = next_node
→ s = 0
→ 从剩余路径取新的 next_node
→ 由入边/出边计算 LEFT 或 RIGHT
→ 完成规划要求的直行、转向或倒回动作
→ current_edge = 新的出边
→ 开始累计新边的 s
```

实现时需要明确“到点后更新节点”和“转完后进入新边”两个时刻，避免转弯失败时软件却已经认为车辆在下一条边上。

## 异常处理

- 预计到达 `patrol_slot`，但唯一一次 200 mm 接近结束后仍没有有效卡：立即锁定停车报警，不继续盲走，不伪造到达和播报。
- 在普通 `junction` 收到卡：立即停车并报告拓扑或场地不一致，不能用卡号擅自跳转节点。
- `present=1, card_number=0`：表示可能看见了卡但认证、读块或编号有效性未完成，只记录诊断，不触发转弯。
- 收到 1～12 中的卡号但与已建立映射冲突：停车并报告冲突，不覆盖旧映射。
- 视觉路口出现得比预计边长明显过早或过晚：保持当前拓扑节点，进入定位异常，不能继续累计错误路径。
- UART 链路断开或 RFID 数据超时：有标签节点禁止仅凭旧的 RFID 帧触发动作。

## 局部测试约定

从图示①和②之间开始、向图示②的固定位置测试时，应在启动参数中明确测试起点、车头朝向和目标 `slot_id`。验收关注的是：

1. 视觉把车带向预期固定位置；
2. 只在 `generation` 变化时产生一次读卡事件；
3. 车辆停车后旋转中心位于可安全转弯的位置；
4. 转向方向来自拓扑路径；
5. 读到的实际 `card_number` 被记录和显示，不要求它等于图示②；
6. 转完能够重新捕获下一条道路。

当前局部测试代码已经完成下位机读卡、`RFID_CARD` 上报、上位机事件显示，以及“首次有效读卡 → 零速停稳 → IMU 转 90° → 视觉重新捕获”的一次性串联。完整的多节点拓扑状态推进与卡号映射仍属于后续任务层实现。

局部实车测试命令（从图示②下方向上行驶、到②后向右转时）：

```bash
cmake -S . -B build-turn -DBUILD_TESTS=ON
cmake --build build-turn -j --target uart_vel
PYTHONPATH=navigation:vision python3 -m road_follow \
  --drive \
  --turn-at-rfid right \
  --uart-bin build-turn/uart/uart_vel
```

若实际摆车方向相反，应把 `right` 改为 `left`。该模式只响应本进程启动后的第一张有效卡；完成一次转弯并重新捕获道路后继续视觉循迹，后续卡不会再次触发转弯。不要同时使用 `--turn-at-junction` 和 `--turn-at-rfid`。

## 赛场标签格式待确认

规则只写“UID 标签”，没有规定卡号的存储格式。当前下位机读取 MIFARE 扇区 0、Block 1 的第 0 字节作为 `card_number`，并使用默认 Key A。正式联调前必须向组委会确认标签是否采用该格式；如果现场只提供原始硬件 UID，则需要扩展上下位机协议并建立 UID 到编号的映射。
